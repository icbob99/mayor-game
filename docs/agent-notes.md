### База данных

- Единственный порядок — `db_deploy.py:SQL_FILES`; server.py использует тот же runner. Не копировать список в тесты. Номер в имени SQL не равен позиции журнала.
- Schema 003 **уже в production**. UI-таблица — `game_locale_ui`, переименование отменено. Legacy events/locales уже удалены; drop повторять не нужно.
- Production принят через baseline; повторять его не нужно. check-baseline сравнивает с исходным состоянием до миграции журнала, а не с текущим релизом.
- Проверить: `python -B db_deploy.py status --env-file .secrets/production.env`.
- Применить согласованные SQL: `python -B db_deploy.py apply --env-file .secrets/production.env`.
- Runner сверяет порядок/checksum; каждый файл и запись applied фиксируются одной транзакцией. Повтор пропускает применённые файлы. После обрыва проверить журнал, не запускать SQL вслепую.
- Компенсация в db/rollbacks не автоматическая: при разрешённом возврате добавить её новой записью в SQL_FILES, не стирать историю. Журнал не заменяет backup.
- Проверить обновление существующих данных и компенсацию, затем status и затронутые данные/API. Свежий стенд не доказывает upgrade; SQLite не равен libSQL/браузеру.
- Для публичного /api/game-data проверен Node fetch; Python urllib ранее получил 403. Для SELECT использовать Database из db_deploy.py с env. В PowerShell перед передачей Unicode в stdin задавать UTF-8 OutputEncoding либо применять apply_patch: иначе кириллица может превратиться в вопросительные знаки.

- При изменении контракта: совместимый SQL → Worker → проверка API → frontend → публичная проверка. Только тексты БД не требуют деплоя Worker/сайта. Не выпускать frontend поверх несовместимого Worker.
- Сайт публикуется через master/GitHub Pages; источник Pages проверить перед автоматизацией. Push не доказывает завершённую публикацию сайта.

## Принятый игровой дизайн

### D01. Гость, регистрация и вход

- Первый визит — гость без навязанной регистрации. «Я мэр» открывает вход, «Хочу быть мэром» — регистрацию по нику/паролю. Неизвестный ник и занятый ник имеют понятные ошибки.
- `Boris`, `boris`, ` Boris ` — один nickname_key; отображение сохраняет выбранный регистр без крайних пробелов. Email, восстановление пароля, город, аватар, постоянный титул и выбор темпа не добавлены.
- Гость хранится локально, но его игра/история/статистика не переносятся в аккаунт. Новый аккаунт начинает новую игру.
- Незарегистрированному гостю предложить регистрацию после 3-й, 8-й, 18-й завершённой игры. После отказа на последнем приглашении не докучать; не показывать приглашение при загрузке страницы.

### D02. Переключение мэр/гость

- «Хочу быть гостем» сохраняет мэра отдельно и начинает гостевую игру с нуля. Гостевые ходы не изменяют мэра и не завершают авторизацию.
- Последний режим запоминается. Возврат при действующей авторизации — без пароля, в том числе после гостевых ходов. При истечении авторизации требуется вход. Офлайн сохраняется локальный прогресс; автоматической очереди повторных PUT нет.

### D03. Другая вкладка или устройство

- Аккаунт может иметь несколько авторизаций, но только один серверный writer. Один login в B не отключает A.
- При переносе подтверждение «Продолжить игру здесь?» даётся на новом устройстве; ответ старого не требуется. Только подтверждение передаёт право записи. Старое окно не захватывает его обратно автоматически.
- Сервер проверяет writer при записи. Офлайн-вкладку невозможно мгновенно отключить; после возвращения связи она не получает право записи сама.
- ID вкладки находится в sessionStorage; Web Lock защищает от копирования при дублировании. Авторизация — `mayorAccount:tab:<id>:auth`, игра — `mayorAccount:<account>:tab:<id>:cloudSave`; общий `mayorAuth` хранит указатель и метаданные без токена.
- Закрытую вкладку можно восстановить по указателю и освободившемуся Web Lock. Чужая/старая вкладка не перезаписывает указатель активностью или expiry. Без Web Locks fallback создаёт новый ID; бесшовный reopen для него не заявлен.

### D04. Бездействие и авторизация

- Через 25 минут без действий — предупреждение, через 30 — локальное сохранение и блокировка мэра до входа. Действие игрока/«Продолжить» сбрасывает таймер; фоновые GET/PUT не считаются активностью.
- Правило действует офлайн, при сне и возврате из фона; учитывается реальное прошедшее время. Активная офлайн-игра продолжается, но серверная авторизация может истечь; после входа локальный прогресс сохраняется.
- Успешный login в одной транзакции удаляет просроченные/отозванные auth_sessions этого аккаунта, кроме строки, на которую ссылается active_game_sessions. Живые независимые авторизации остаются. Очистка запускается входом, не таймером; жёсткий лимит живых сессий не введён.

### D05. Persistence и выбор продолжения

- **Отправили и забыли:** каждое изменение сначала сохраняется локально, затем полный снимок отправляется один раз. Ход не ждёт ответа. Ответ обычного PUT, включая ошибку, не меняет игру и не запускает повтор.
- Нет очереди pending, ackTimestamp или completedGames. Timer/online/focus/reload не переотправляют обычный снимок. Следующее действие отправляет новое состояние. Потерянное завершение не повторяется при начале следующей партии; абсолютная статистика входит в новые снимки, а строка истории потерянного завершения может отсутствовать.
- Интерактивная активация/подтверждение переноса — отдельный механизм с ответом и operationId. Восстановление её потерянного ответа допустимо; фоновое восстановление активации не отправляет save.
- GUID облачного сохранения назначает сервер. Он используется при выборе/активации, не проверяется на каждом собственном PUT. Проверка writer и возрастающего writeTimestamp защищает записи после активации.
- При входе/выборе сохранять свою локальную ветку. Если исходное облако не менялось — можно продолжить локальное; если обе версии различаются — показать день/капитал/завершённость и дать выбор. Не складывать прогресс и не выбирать «лучший» автоматически. Повторно проверить увиденный GUID перед заменой.
- Собственное фоновое сохранение не должно создавать ложный конфликт. Проверяются текущий writer и равенство state/stats независимо от порядка JSON-ключей; localChanged отмечает локальную ветку, включая явный выбор local. Чистую копию можно заменить облаком без бессмысленного диалога.
- Повторный вход/явный выбор local может отправить текущий снимок один раз. Обычный reload действующего writer сохраняет локальную игру без новой активации/повторной отправки. Истечение авторизации или закрытие вкладки сами по себе не являются конфликтом.
- Состояние одного аккаунта никогда не отправлять в другой. GET/активация, пришедшие позже локального хода, не должны его затереть.

### D06. Состояние и история

- Сохраняются игровой день, показатели, кулдауны, все достижения (включая нули), признак и причина завершения. Магазин сохраняется каждый ход/после покупки.
- После повторного открытия — новая карточка; прошлые очереди последствий отменяются. Текущая карточка, порядок ответов, eventQueue и журнал решений в снимок не входят. Во время смены языка текущий порядок ответов сохраняется.
- Завершение и статистика учитываются один раз. История содержит gameId, дату, дни, капитал, причину и достижения. `rookie/master/legend` — результаты завершения, не постоянный титул.
- Создание отдельного нового мэра/персонажа отложено. Выбор продолжения не разрешает стирать накопленную историю.

### D07. Локальный Docker-стенд

- `python server.py` пересоздаёт **ручной** `mayor-game-dev`, включая удаление его БД/volume. Игра http://localhost:8787, БД http://localhost:8081. Не запускать при разборе сохранённого аккаунта Бориса без разрешения на сброс.
- `python server.py --test` пересоздаёт отдельный `mayor-game-test`, порты 8788/8082. Два контейнера: страница/Worker и настоящий libSQL. Прежний Python-эмулятор удалён.
- Единственный порядок SQL — `SQL_FILES` в db_deploy.py; server.py вызывает общий apply, не копировать список в тесты. Скрипт собирает game с `--no-cache`, проверяет готовность и печатает URL; браузер сам не открывает. Чужие Docker-проекты/volumes не трогать, global prune не использовать.
- `db:8080` доступен внутри Compose, не с Windows. В db-образе не было sqlite3/curl/wget; для ручных SELECT уже настроен Database Client. Не править файл живой БД напрямую.

### D08. Сброс локального браузера

- При пересоздании меняется DEV_INSTANCE_ID; при обычном reload он прежний. До загрузки сохранений локальный клиент запрашивает поколение стенда. Если getInstance завершается ошибкой, разрешено восстановить только ранее известный ID; без него загрузка отклоняется. После возвращения связи проверка поколения продолжается.
- Новый ID очищает только ключи этой игры: гость/статистика/авторизация/сохранения/приглашения. Чужие ключи localStorage сохраняются.
- Старая вкладка отправляет старый ID и получает отказ, очищается и перезагружается; не может записать старый прогресс в новую БД. В production этого механизма нет.

### D09. Сложность (баланс выпуска 2026-11-23)

- Выбор в native dialog из шапки и Game Over; только названия, без описаний механик. Четыре кнопки, активная выделена, закрытие крестиком/фоном/Escape. Порядок шапки: название, звук, рынок, сложность, достижения, язык; RTL зеркально.
- Default normal. На day=1 смена немедленная (включая после покупки); day>1 требует локализованного confirm и resetGame(выбранный уровень). Отмена/выбор текущего уровня ничего не сбрасывают. После Game Over другой уровень начинает новую партию без подтверждения; обычная кнопка нового срока сохраняет выбранный уровень. difficultyLocked удалён, состояние определяется day/isFinished. Старые сохранения без difficulty получают normal.
- `app/game/difficulty.js`: версия выпуска easy gain/loss 1/1, normal 1/1 плюс модификаторы шкал и initialHealth 77 (параметры и проверка переноса выше), hard 0.8/1.3, insane 0.6/1.6. Остальные уровни стартуют с health 90. До этого выпуска easy был 1.2/0.8, normal без новых модификаторов. Рост threat вреден; остальные положительные эффекты выгодны. Округляется модуль, затем возвращается знак; для нового Normal сначала отдельно округляется модификатор шкалы.

- Покупки не считаются ходами и не масштабируют бонусы перков. Каждый успешно купленный перк дорожает на 50% с округлением, кроме easy (цена всегда базовая). Cooldown сохранён. difficulty/shopPrices входят в локальный и облачный снимки; обычные PUT остаются send-and-forget.

Старый Worker отвергает новые endReason; старый frontend теряет настройки сложности при записи. После появления новых партий полноценный откат приложения несовместим — нужен совместимый forward fix. SQL-компенсация возвращает только переводы, не игровой контракт.

Нагрузка: один GET при активации профиля, один UPDATE/INSERT после серии изменений; обычный игровой render запросов не добавляет.

## P2. Контракт данных и API

- JSON camelCase, SQL snake_case; время — UTC Unix milliseconds. Bearer определяет аккаунт, не входящий accountId. Язык — настройка браузера; новая аудиосистема синхронизирует звук с профилем отдельно от партии (D11).
- Снимок содержит state и абсолютные stats, не дельты. gameId — UUID партии; показатели 0–100, cooldowns — дни доступности. Достижения в state — 0/1, в stats — количество завершений; maxMoney учитывает текущую игру. Точные поля/ключи/валидация — `app/game/mayor-save.js`, `cloudflare/saves.js`, SQL — `cloudflare/game-storage.js`; не поддерживать вторую полную копию JSON здесь.
- `writeTimestamp = Math.max(Date.now(), previousWriteTimestamp + 1)`; после выбора local — также больше облачной метки. versionGuid/updatedAt назначает сервер. GUID защищает выбор/активацию, timestamp — порядок записей; operationId не заменяет timestamp. Триггер game_statuses_reject_stale_update запрещает меньшую/равную метку; штатный SQL отфильтровывает её заранее.
- PUT `/api/game/save`: `{gameSessionId,writeTimestamp,state,stats}` → 204, stale/equal тоже 204 без записи. Один DB batch проверяет auth/writer/timestamp, обновляет status/stats и при завершении добавляет историю. Ошибка истории откатывает всё; PK(account_id,game_id) предотвращает дубль. Stale save не добавляет историю. Обычный save не читает/пишет квитанции.
- PUT `/api/game/session`: `{operationId,expectedVersionGuid,previousGameSessionId?,confirmTransfer,source}` → `{gameSessionId,save}`. Source local/cloud; чужой writer без подтверждения → transfer_required, изменившийся GUID → save_conflict. Повтор operationId сравнивает request_hash; сохранённый ответ доступен только пока сессия остаётся writer.
- GET `/api/game-data` остаётся raw для DAL. Auth и остальные endpoints/errors проверять в worker.js/auth.js/saves.js и тестах. Обычный PUT не использует ответы для UI/retry; интерактивные запросы обрабатывают ошибки согласно D03–D05.

## Offline и проверки

- Offline reload требует предварительной установки service worker и кэширования сайта/game-data. Сеть первая, fallback при сетевом исключении, не HTTP 4xx/5xx. Auth/save/session не кэшируются и не повторяются. Первый запуск без сети не поддерживается.
- Кэш стенда проверяет поколение; новые данные заменяют старые по одному URL. При откате frontend зарегистрированный worker не исчезает: полное удаление требует unregister/cleanup без стирания сохранений.
- DAL-тесты — raw in → объекты out, без Python/БД/копии SQL. Dev/local-environment тесты оставлены по решению Бориса. Новый framework не вводить.
