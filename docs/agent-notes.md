## Термины

| Термин | Значение |
| --- | --- |
| Гостевая игра | Отдельная игра и статистика браузера, без переноса в аккаунт |
| Игра мэра на устройстве | Сохранение зарегистрированного мэра в браузере, включая неотправленные изменения |
| Облачная игра мэра | Последнее принятое сервером сохранение того же аккаунта |
| GUID сохранения | Метка принятой облачной записи; нужна для проверки равенства, а не для определения дня или лучшего результата |
| Авторизация | Право аккаунта обращаться к API; истечение не удаляет игровой прогресс |
| Активная игровая сессия | Устройство/вкладка, которому сервер разрешает сохранять игру после входа/подтверждения переноса |
| ID операции | Техническая метка конкретной отправки для распознавания повтора; не путать с GUID облачного сохранения |
| ID локального стенда | Метка полного пересоздания Docker-стенда; не связана с аккаунтом, авторизацией или GUID сохранения |

## Принятый игровой дизайн

### D01. Гость, регистрация и вход

- Первый визит начинает гостевую игру без навязанного окна регистрации.
- Две отдельные кнопки: «Я мэр» и «Хочу быть мэром».
- «Я мэр»: ник и пароль, затем сохранённая игра аккаунта. Неизвестный ник — ошибка и предложение зарегистрироваться. Восстановления доступа пока нет.
- «Хочу быть мэром»: новый ник и пароль. Занятый ник — ошибка, свободный — регистрация и новая игра мэра.
- Проверяется уникальность ника. `Boris`, `boris` и ` Boris ` считаются одним ником. Отображаем выбранный регистр без пробелов по краям.
- Сложность пароля, email, подтверждение регистрации и восстановление доступа не вводить. Не смешивать это с необходимой серверной проверкой формата запроса и безопасным хранением пароля.
- Гостевое сохранение в браузере остаётся. Борис явно уточнил: отменяется перенос в аккаунт, а не локальное хранение гостя.
- Новый мэр не наследует гостевую игру, историю или статистику.
- Предлагать регистрацию после 3-й, 8-й и 18-й завершённой гостевой игры. После отказа на последнем приглашении больше не докучать; не открывать приглашение при загрузке сайта.
- Не возвращать поля города, аватара, постоянного титула или темпа из отменённой реализации: новый пользовательский сценарий регистрации содержит ник и пароль.

### D02. Переключение мэр/гость

- В режиме мэра есть «Хочу быть гостем».
- Сначала сохраняем мэра локально отдельно от гостевых данных. При доступном сервере отправляем в облако.
- Начинаем гостевую игру с нуля. Прогресс и статистика мэра не изменяются гостевой игрой.
- Переход доступен без связи. Неотправленное сохранение мэра остаётся ждать отправки; восстановление связи подчиняется D05.
- Переход к гостю сам по себе не завершает авторизацию; её срок определяется D04.
- Запоминаем последний выбранный режим. Повторный вход не требуется, пока авторизация действительна.

### D03. Другое устройство или вкладка

- Одна активная серверная игровая сессия аккаунта. Ограничение относится и к нескольким вкладкам одного браузера.
- После проверки ника и пароля на новом устройстве при переносе показываем: «Продолжить игру здесь? Предыдущая игровая сессия будет отключена».
- Подтверждение выполняется на НОВОМ устройстве. Ответ старого компьютера не требуется: он может быть выключен.
- После подтверждения сервер лишает старую сессию права сохранять и разрешает новую. Загружается доступное облачное сохранение; наличие своего неотправленного прогресса обрабатывается по D05.
- Старое окно не может автоматически вернуть себе право записи. Для переноса обратно требуется вход и подтверждение.
- Проверять право записи на сервере в момент сохранения, а не только отключать кнопки клиента.
- Офлайн браузер невозможно мгновенно отключить удалённо. Он может продолжать локальную игру; при возвращении в сеть устаревшая сессия не получает права записи автоматически.

### D04. Бездействие и авторизация

- Таймаут — 30 минут БЕЗ ДЕЙСТВИЙ игрока. Ранее предложенные 30 дней отменены.
- Через 25 минут бездействия: предупреждение о выходе через 5 минут и действие «Продолжить».
- Активность игрока/«Продолжить» сбрасывает таймер. Фоновые сохранения и служебные запросы сами по себе активностью не являются.
- Через 30 минут: сохранить доступный локальный прогресс, завершить авторизацию, заблокировать игру мэра до повторного входа. Вкладку не закрывать.
- Правило действует и без интернета. После офлайн-выхода повторный вход требует связи.
- Проверять реальное прошедшее время при возврате из сна/фонового режима. Не полагаться только на срабатывание браузерного таймера. После ночи требуется вход.
- Если игрок активно играет офлайн, не блокировать игру только из-за отсутствия связи. Серверная авторизация за это время может истечь: перед отправкой потребуется вход, игровой прогресс остаётся.
- Хранить данные для восстановления авторизации, а не пароль. Продление сессии при активности не обязательно требует нового токена каждый раз.
- После повторного входа того же аккаунта применять D05. Авторизация сама по себе не должна перезаписать ожидающий отправки игровой прогресс.
- Уточнение 2026-10-31: вход в B не отключает A до подтверждения переноса. По команде «давай чинить здесь и сейчас» одобрена очистка auth_sessions: при успешном login удалить отозванные/просроченные строки вошедшего аккаунта в той же транзакции, сохранив авторизацию, на которую ссылается active_game_sessions. Действующие независимые авторизации сохраняются; жёсткий лимит их количества не вводился. После смены владельца прежняя недействующая запись удаляется при следующем успешном входе. Если новых входов нет, очистка сама по таймеру не запускается, но и новые строки не добавляются.

### D05. Офлайн-игра, отправка и конфликт

- Игровая логика остаётся в браузере. Игрок может активно играть без связи; сеть не является условием следующего хода.
- Фоновое сохранение состояния: «отправили и забыли» (повторно подтверждено Борисом 2026-10-31 как исходная договорённость). Не сохранять прежний запрос для автоматической повторной доставки и не строить очередь ожидания подтверждений. Следующее изменение отправляет новый актуальный снимок; writeTimestamp защищает сервер от запоздалых записей. Это требование относится к фоновому persistence, отдельно от входа/выбора продолжения.
- Хранить прогресс мэра на устройстве с привязкой к аккаунту и GUID облачного сохранения, от которого он продолжал игру.
- Новый GUID создаёт СЕРВЕР при каждом принятом обновлении облачного сохранения. Устройство не увеличивает счётчик и не назначает облачные GUID самостоятельно.
- Уточнение принятого контракта 2026-10-30: исходный GUID проверяется при восстановлении/выборе продолжения и выдаче права записи. Дальнейшие фоновые PUT проверяют активную игровую сессию и возрастающий `writeTimestamp`, а не равенство GUID на каждом PUT; собственные параллельные записи не должны создавать ложный конфликт. Каждая принятая запись получает новый серверный GUID.
- GUID совпал — автоматически сохранить прогресс с устройства.
- GUID не совпал — предложить выбор: оставить текущую игру мэра на устройстве или загрузить облачную. Это НЕ выбор гостевой игры.
- До выбора не перезаписывать ни одну из конкурирующих версий.
- «Оставить игру на этом устройстве» заменяет облачную выбранным состоянием; «Продолжить облачную» заменяет состояние мэра на устройстве облачным.
- Показать день, капитал и состояние игры (продолжается/завершена), чтобы варианты можно было различить.
- Прогресс двух продолжений не объединять, не складывать деньги и не выбирать автоматически больший день.
- Даже при явном выборе проверять GUID облачной версии, которую игрок видел: за время выбора облако могло измениться ещё раз.
- Прежняя запись о повторе фонового сохранения после потерянного ответа была расширением агента и противоречит «отправили и забыли»; не использовать её как основание для pending/retries. Сохранность локального состояния и выбор продолжения остаются требованиями.
- Истечение сессии, закрытие вкладки или перерыв на сутки сами по себе не создают конфликт сохранений.
- Пример: играл на одном устройстве офлайн, вернулся через сутки, облачный GUID тот же — после входа автоматически отправить прогресс.
- Без неотправленных локальных изменений можно загрузить актуальное облачное сохранение; не предлагать бессмысленный выбор одинакового/неизменённого состояния.
- Никогда не отправлять ожидающее сохранение одного аккаунта в другой после смены пользователя.

### D06. Продолжение и история

- Переносим игровой день, деньги и остальные параметры, кулдауны магазина, достижения и признак завершения. Состав остальных полей снимка уточняется в P2.2.

## Принятый локальный стенд

### D07. Docker под управлением server.py

- Единая пользовательская команда: `python server.py`.
- Скрипт управляет Docker-стендом, а не дублирует игровое API на Python.
- Два контейнера: сервер игры (страница + API, код Worker) и libSQL server. Самописный Python-эмулятор не является БД нового стенда.
- Каждый запуск — полный сброс: остановить/удалить предыдущие контейнеры и volume ЭТОГО проекта, заново собрать образы, создать пустую БД, применить миграции и seed, запустить игру.
- Тестовые аккаунты, сохранения и история предыдущего стенда удаляются намеренно. Вариант сохранения БД по умолчанию и отдельный `--reset-db` не выбран.
- Не удалять ресурсы других Docker-проектов; не использовать глобальный Docker prune.
- Проверять готовность БД до миграций и сервера до сообщения об успехе. При ошибке шага показывать её и не сообщать о готовом стенде.
- Выводить один адрес игры. Отдельного ручного запуска Go Live, Worker и БД не требуется.
- Автоматические тесты используют отдельную временную БД/изолированный стенд, не уничтожают ручную проверку случайным запуском тестов.
- Docker предназначен для локальной разработки и проверки. Перенос production в Docker не согласовывался; текущие сервисы — GitHub Pages, Cloudflare Worker и Turso.

### D08. Полный сброс данных браузера локального стенда

- При каждом полном пересоздании генерировать новый `instance_id` и передавать локальному серверу. Он постоянен в пределах жизни этого поколения стенда.
- Перед чтением/восстановлением сохранений браузер получает ID локального стенда (обсуждался endpoint `/api/dev-info`).
- Если запомненный ID отсутствует или отличается: удалить только данные этой игры для локального окружения — гостя и статистику, авторизацию, сохранения мэра/ожидающие отправки и счётчики приглашений; запомнить новый ID, начать гостем.
- Обычная перезагрузка страницы в том же поколении стенда ничего не сбрасывает.
- Старые открытые вкладки передают прежний ID; новый сервер отклоняет такие запросы. Вкладка очищает устаревшее состояние и перезагружается; старый прогресс не попадает в свежую БД.
- Этот механизм отсутствует в production. Не применять безусловный `localStorage.clear()` ко всему origin и не читать/удалять профиль браузера из Python.

Это согласованный формат для последующей реализации, а не заявление о работающем API. Внешние поля JSON — camelCase; столбцы SQL — snake_case. Данные гостя и разных аккаунтов разделены. Язык/звук — настройки браузера. Даты — UTC Unix milliseconds.

**Состояние (`state_json`):**

```json
{
  "gameId": "57fc1190-02a4-4cf0-bbf3-8ba1dd5c8bf9",
  "day": 1,
  "money": 1000000,
  "health": 90,
  "wife": 50,
  "threat": 15,
  "rating": 50,
  "cooldowns": { "police_bribe": 0, "wife_spa": 0, "assuta_vip": 0, "pr_agency": 0 },
  "achievements": { "offshore_king": 0, "untouchable": 0, "happy_wife": 0, "survivor": 0 },
  "isFinished": false,
  "endReason": null,
  "finishedAt": null
}
```

- `gameId` создаётся в браузере при начале партии и остаётся постоянным до конца. Новая партия — новый ID.
- Health/wife/threat/rating — числа 0–100. Cooldowns — игровые дни повторной доступности покупок; 0 — доступно сейчас.
- Все достижения присутствуют. В текущей партии значения 0/1, в накопленной статистике — число завершённых партий с этим достижением.
- Причины окончания: `arrest`, `wife_left`, `heart_attack`, `elections_lost`. Для продолжающейся партии причина/время — null. Для законченной партии сохраняем результат и показываем завершение после загрузки.
- Карточка, порядок ответов и очереди последствий не входят в снимок; после повторного открытия продолжающейся партии — новая карточка.

**Статистика (`stats_json`):**

```json
{
  "gamesPlayed": 0,
  "maxMoney": 0,
  "achievements": { "offshore_king": 0, "untouchable": 0, "happy_wife": 0, "survivor": 0 }
}
```

`maxMoney` учитывает достигнутый капитал, включая текущую партию. Это абсолютный снимок, а не приращения при каждом PUT.

**Авторизация:**

| Запрос | Тело | Успешный результат |
| --- | --- | --- |
| `POST /api/auth/register` | `{ nickname, password }` | `{ account: { id, nickname }, authToken, expiresAt, activeGameSessionId: null }` |
| `POST /api/auth/login` | `{ nickname, password }` | Та же форма, `activeGameSessionId` может указывать на уже активную игру |
| `POST /api/auth/activity` | Без игровых данных; только по действию игрока | `{ expiresAt }` |
| `DELETE /api/auth/session` | Без тела | Авторизация отозвана; сохранения не удаляются |

- Новый аккаунт без переноса гостевой игры. Ники сравниваются без крайних пробелов и без учёта регистра; display сохраняет регистр. Пароль хранится только как хеш; браузер сохраняет opaque token. Защищённые запросы передают `Authorization: Bearer <authToken>`, аккаунт определяется по авторизации, не по доверенному входящему accountId.
- Поведение таймаута — D04: предупреждение 25 минут, выход 30; фоновые сохранения не являются активностью. Офлайн-продолжение доступной игры не отменяет таймаут. Новый логин/регистрация требуют связи. Переход в гостя не является logout.

**Загрузка:** `GET /api/game/save` возвращает `null`, если сохранения нет, иначе `{ versionGuid, writeTimestamp, updatedAt, state, stats }` с полными снимками выше. Без локальных изменений загружаем облако. Если локальные изменения есть и исходный GUID прежний — автоматически продолжаем/отправляем локальное. Если GUID другой — выбор игрока (день, капитал, завершённость); до выбора обе версии сохраняются. Прогресс не объединяем.

**Активация/выбор:** `PUT /api/game/session` принимает `{ operationId, expectedVersionGuid, previousGameSessionId, confirmTransfer, source }`; source — `local`/`cloud`, expectedVersionGuid — увиденная облачная версия или null. Необязательный previousGameSessionId — UUID прежнего владельца этой вкладки; без него автоматическая активация разрешена только при отсутствии текущего владельца. Совпадение текущего gameSessionId позволяет обычный reload/повторный вход; иначе требуется confirmTransfer=true, даже при совпадении auth token. Сервер атомарно проверяет GUID и разрешение переноса, назначает новую активную сессию. Ответ `{ gameSessionId, save }`. Изменившийся GUID даёт `409 save_conflict` с актуальным save; неподтверждённый перенос — `409 transfer_required` с save. Повтор operationId возвращает прежний результат только пока эта сессия остаётся владельцем; после замены — 403, без восстановления права записи.

**Проверка владельца:** `GET /api/game/session?gameSessionId=<UUID>` возвращает `{ gameSessionId }`, если активная игровая сессия и её auth_session_id принадлежат вызывающему токену. Иначе `403 session_replaced`; просроченная авторизация — 401. Проверка не продлевает idle-время. Браузер блокирует старую вкладку до повторного входа и подтверждения; недоступная сеть оставляет локальную игру доступной до её обычного idle-таймаута.

При выборе cloud браузер заменяет локальное состояние облачным. При выборе local сохраняет своё и отправляет его с timestamp больше полученного облачного. После активации конкурирующие PUT защищены сессией/timestamp, а не сравнением GUID каждого собственного запроса. Повторное получение уже обработанного operationId не выдаёт заново отозванное право записи.

**Фоновая запись — согласованный контракт 2026-10-31:**

`PUT /api/game/save` принимает `{ gameSessionId, writeTimestamp, state, stats }`. Сначала браузер сохраняет локальный снимок, затем отправляет его один раз. Следующий ход не ждёт предыдущего PUT. Ответ, включая ошибку, не изменяет игру и не запускает повтор. Успешный ответ — 204 без тела; для старой/равной метки тоже 204 без изменений БД.

- `writeTimestamp = Math.max(Date.now(), previousWriteTimestamp + 1)`; после явного выбора local метка также больше прочитанной облачной. `updatedAt` и новый GUID назначает сервер. Обычный PUT не содержит operationId и не создаёт квитанций.
- В state уже есть isFinished, gameId, finishedAt, day, money, endReason и achievements. Если партия завершена, сервер из этого же снимка создаёт строку game_history. Отдельного массива completedGames и клиентского подтверждения удаления окончаний нет.
- История уникальна по (account_id, game_id); статистика — абсолютные значения. Новый ход передаёт актуальный снимок, не накопленные запросы. Потеря последнего запроса означает, что его состояние/окончание могут остаться только в браузере; гарантии доставки нет. Начало новой партии не повторяет окончание предыдущей.

**Транзакция записи:** проверить авторизацию/активного владельца и более новый timestamp; обновить state/stats/GUID/updatedAt; добавить результат завершения только если этот снимок принят. Один DB batch и одна транзакция; ошибка history откатывает также status/stats. Старые запросы не добавляют историю. Результат обычного PUT не хранится в game_persistence_operations. Квитанции интерактивной активации пока сохраняются по прежнему контракту.

1. **Локальное состояние и отправка** (`app/game/mayor-save.js`, `app/game/account-session.js`).
